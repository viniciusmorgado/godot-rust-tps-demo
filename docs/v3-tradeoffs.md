# v3 trade-offs — engine touch points

Where the ECS abstraction touches the engine (constitution 1.5.1, Principle I v3 and Principle
III "ECS shape"). One row per touch point, added in the commit that introduces it.

| Module | What the engine owns | Why the ECS cannot hide it | How the sync layer handles it | Location |
|---|---|---|---|---|
| `part`, `level`, `red_robot` | Scene instancing: `PackedScene::instantiate` + `add_child` (and the `ready` that follows) | The node must exist before it can be a view of an entity; instancing stays in the v2 node code of the spawner (Principle I v3 scope: `level` is excluded from the ECS, `part`/`red_robot` are later milestones) | The spawned node's bridge pushes `InboundEvent::Register` from its own `ready`; the drain of the next schedule run spawns the entity (`ecs::apply_register`), so the spawner never touches the World | `part.rs:116-117` (preload) / `:196-205` (instantiate in `destroy`), `red_robot.rs:423-425`, `level.rs`'s prefab spawner; `ecs.rs::apply_register` |
| `part_disappear`, `blast` | Frame time (`_process` delta) and the `SceneTreeTimer`s v2 awaited | The ECS cannot hide time itself: a tick timer can only be as exact as the delta the engine hands the driver | `EcsWorld::process` writes `FrameDelta` before the frame schedule; the `Timer` component reproduces `SceneTree::process_timers`' subtractive arithmetic (`time_left -= dt`, fires when `<= 0`, research.md R5) so it expires on the same step as the `SceneTreeTimer` it replaces; `DisappearPhase::advance` steps it in `Phase::Gameplay`, `sync_out_puff`/`sync_out_remove` apply the outcome | `ecs/timer.rs`, `part_disappear/system.rs`, `ecs.rs::sync_out_puff` |
| `blast` | Animation playback and its end: `animation_finished` is emitted by the `AnimationPlayer`'s own idle processing | The animation's end is engine time, not tick time — the ECS cannot compute when the engine's own animation will finish | The bridge receives the child's signal through a typed `connect_other` into a `#[func]` that only pushes `BlastAnimationFinished`; the drain (`ecs/apply.rs`) resolves the id and inserts `Remove`; `sync_out_remove` `queue_free()`s the node in the same frame's `SyncOut` | `blast.rs`, `ecs/apply.rs::apply_non_register`, `ecs.rs::sync_out_remove` |
| `blast` | The camera's global transform, and `look_at` (`Basis::looking_at`, engine-backed under the 1.4.1 rule) | The value the decision needs lives in the engine and changes every frame the camera moves; the write is an engine-backed rotation, so a pure step would have nothing to compute | Sync-only entity (NO gameplay system): `sync_in_blast` reads the cached camera's origin once per distinct camera per frame into `LookTarget` with `set_if_neq`; `sync_out_blast` calls `look_at` on `Changed<LookTarget>`. Measured explicit engine calls per blast per frame, by reading the two systems: `is_instance_valid` (camera) + `get_global_transform` + `look_at` = 3, v2's count (`blast.rs:42-47`), plus the FR-009 root validity sweep for a lone blast; the camera calls are shared, so ≤ 3 + sweep from two concurrent blasts — FR-025 as amended | `ecs.rs::sync_in_blast`, `ecs.rs::sync_out_blast` |
| `player` | Root motion: the displacement/rotation the `AnimationTree` accumulated since its last advance (`get_root_motion_position/rotation`) | The animation drives the body: a pure step cannot know how far the walk cycle moved the model this step | `orient_and_anim` (`EngineQueryOrient`) reads it once per step into `RootMotion` (never while airborne, v2 `player.rs:258`); `tick_integrate` (`GameplayIntegrate`) integrates it with `integrate_root_motion` unchanged | `player/sync.rs::orient_and_anim` |
| `player` | `move_and_slide` and the post-move origin (`CharacterBody3D`) | The body's collision response is the physics server's answer; the respawn decision needs the origin AFTER it | `move_body` (`EngineQueryMove`) sets the velocity computed by `tick_integrate`, calls `move_and_slide`, reads `origin.y` into `BodyState`; `tick_settle` (`GameplaySettle`) decides `should_respawn`; `sync_out_player` applies the reset | `player/sync.rs::move_body` |
| `player_input` | The crosshair raycast (`PhysicsDirectSpaceState3D::intersect_ray` from the camera's projected ray), AFTER this frame's camera rotation | The ray origin/direction come from the engine-computed camera transform through the `SpringArm3D` chain; the rotation writes must precede it in the same frame (v2 `player_input.rs:94-95` before `:117-119`) | `camera_and_ray` (frame `EngineQuery`) applies the camera deltas in v2's order (mouse first, then controller, `clamp_pitch` on the live rotation), THEN raycasts when shooting; `shoot_target` is projected into the input node by `sync_out_input` | `player_input/sync.rs::camera_and_ray` |
| `player` | Engine-backed rotation math: `Quaternion::slerp`, `Basis::looking_at` (CLAUDE.md's builtin-math rule) | Both go through the engine's builtin methods, so they cannot run in a pure system | `tick_decide` emits the target (`OrientTarget::Camera(q)` / `Walk(target)` from `walk_target`, pure); `orient_and_anim` (`EngineQueryOrient`) slerps the entity's `Orientation` toward it (v2 `player.rs:261-264`, `:296-300`) | `player/sync.rs::orient_and_anim` |
| `player` | Bullet instancing from the tick (`PackedScene::instantiate` + `add_child` under the player's parent, `look_at`, `add_collision_exception_with`) | The bullet node must exist to be shot; its origin is `ShootFrom`'s PRE-move transform (v2 `player.rs:275` precedes `:322`), so the spawn cannot wait for `SyncOut` | `tick_decide` decides `shoot` (`shooting && cooldown_left == 0.0`); `orient_and_anim` spawns the bullet before `EngineQueryMove` runs `move_and_slide`; `bullet.rs` stays v2 code (its bridge is a later milestone) | `player/sync.rs::orient_and_anim` |
| `player` | The `AnimationTree`'s own processing (advance, blend, root-motion accumulation) and its parameter writes | v2's tick ran BEFORE the tree's PHYSICS processing (tree order), reading the previous step's root motion and writing this step's parameters; the driver at `i32::MAX` runs AFTER it, so a PHYSICS-mode tree would give the tick each step's root motion one step early (research R1: `M(n).rm == S(n+1).rm` at every step, positions diverging from step 13) | `player.tscn:592` `callback_mode_process = 2` (MANUAL, the milestone's one scene edit); `sync_out_player` writes the parameters (`apply_anim`, v1's per-variant order — moved out of `EngineQueryOrient`, where they answered nothing) and then, LAST, `advance(FixedDelta)` for EVERY player entity — proven identical to v2 step by step (R1's runs (i) vs (iii): no differences) | `player/sync.rs::sync_out_player`, `oxide-godot/player/player.tscn:592` |
| `player`, `player_input` | Replication (`MultiplayerSynchronizer`) of node properties, sampled in `SceneMultiplayer::poll()` at the top of `SceneTree::process` (after the physics steps, before the frame run, once per rendered frame — research R2) | The wire format is the node's exported fields, not the components; only the engine samples and applies them | Projection: fixed `sync_out_player` writes `Player.motion`/`current_animation` on `Simulates`; frame `sync_out_input` writes `InputSynchronizer.{aiming, shoot_target, motion, shooting}` on `OwnsInput`; fixed `sync_in_player` reads the input node's fields into `InputFrameC` on every peer and, on non-`Simulates`, the replay fields into `ReplayState`; `CameraBase`/`CameraRot` rotations and the transforms replicate from the node values the sync layer writes (contracts/player-entity.md §2) | `player/sync.rs::sync_in_player`/`sync_out_player`, `player_input/sync.rs::sync_out_input` |
| `player` | RPC timing: `jump`/`land`/`shoot` are `#[rpc(authority, call_remote, unreliable)]` (v2: `call_local`) | v2 applied their local effects INLINE in the physics step through `call_local`; a v3 handler could only push an event consumed by the frame run — `FireCooldown` one frame late, shoot trauma after `shake_decide`, and a transient animation write that replication can sample (R2) | Option (b), spec FR-004: the `Simulates` entity's fixed `SyncOut` applies the local effects itself, in v2's order (`Land` sound, `Jump` sound, `Shoot` particles/cooldown/sound/trauma), then sends the RPCs, which reach remote peers only; their handlers push `PlayerFx` for the frame run's `apply_player_fx` (commit 3). Names and signatures unchanged; the attribute is the one deviation | `player.rs` (handlers), `player/sync.rs::sync_out_player` |
